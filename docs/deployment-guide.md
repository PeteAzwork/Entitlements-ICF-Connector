# Deployment guide: Graph Entity Service connector in Ping IDM 7.5

**Audience:** whoever installs the connector into an IDM deployment: IDM platform engineers and operators.
**Scope:** from an IDM 7.5 that has never seen the connector, to a connector that passes its checks, with mappings loaded and ready for the initial load. Then upgrades, rollback and removal.
**Companion:** `docs/runbook.md` covers running it from there: the initial load (§3), schedules (§4), monitoring (§5), logs (§6), the API key (§7), troubleshooting (§8).

Every section says how it was verified:
- **Tested** means exercised against IDM 7.5.0 (`gcr.io/forgerock-io/idm:7.5.0`), by the integration suite (`integration/`) or by the walkthrough script (`dev/deploy-walkthrough.sh`, whose output is [appendix A](#appendix-a-worked-example)).
- **Not tested** means written from the product documentation and the code. Treat it as a plan to check in your environment.

## 1. What gets deployed where

| Where | What | Comes from |
|---|---|---|
| **Each IDM server:** `<idm>/connectors/graphentity/scripts/` | The seven ICF operation scripts (`CreateScript.groovy` and so on) | The connector release zip |
| **Each IDM server:** `<idm>/connectors/graphentity/lib/` | The connector library: Groovy sources under `au/…` (the default), or `graphentity-connector-lib.jar` | The connector release zip |
| **Each IDM server:** `<idm>/script/lib/graphEntityPayload.js` | The mapping library, called by the mappings and the ID-change guard | The connector release zip |
| **IDM configuration:** `config/provisioner.openicf/graphentity` | The connector's configuration: service URL, API key (encrypted by IDM), object types | Generated by the discovery tool, then `createFullConfig` |
| **IDM configuration:** `config/managed` | Reverse relationship properties, and the ID-change guard as each synced type's `onUpdate` | Your `managed.json`, edited |
| **IDM configuration:** `config/sync` | One mapping per synced type, `managed<Type>_systemGraphentity<Type>` | Generated by the discovery tool |
| **IDM configuration:** `config/schedule/recon-graphentity-<type>` | Nightly reconciliations | The release zip's `samples/` |
| **IDM's trust store** (only for a private CA) | The CA certificate of the service's TLS certificate | Your PKI (§5.1) |
| **An operator workstation** | The discovery tool. It reads `managed.json` and writes configuration; it never runs on the IDM servers | The discovery release zip |

The connector itself is IDM's own **Scripted REST connector** (bundle `scriptedrest-connector-1.5.20.21`, shipped with IDM 7.5). This release adds scripts and a library for it, and no bundle, so nothing goes into IDM's `bundle/` directory.

|---|---|---|

| **The Scripted REST connector** | `ls <idm>/connectors` lists `scriptedrest-connector-1.5.20.*.jar` | Shipped with IDM 7.5 |

| **A copy of `managed.json`** | `GET /openidm/config/managed`, or the file from your configuration repository | The discovery tool works from it offline (§6.1) |
| **A decision on the library mode** | Groovy sources (the default) or a jar | `script_vs_jar.md`. Both are tested. Sources are inspectable on the server; the jar initialises faster and can't be edited in place |

## 3. Build the release artefacts

**Tested.** From a checkout of this repository, on the release commit:

```bash
./gradlew :connector:distZip :discovery:distZip
# connector/build/distributions/graphentity-connector-<version>.zip    for the IDM servers
# discovery/build/distributions/graphentity-discovery-<version>.zip    for the workstation
sha256sum connector/build/distributions/*.zip discovery/build/distributions/*.zip
```

- **For the jar mode,** add `-PlibraryAs=jar` to the first command.
- **The connector zip** holds `connectors/graphentity/`, `script/lib/graphEntityPayload.js`, `samples/` (provisioner, mapping and schedule samples) and `VERSION`. `VERSION` records the version, the git commit, the library mode and the build time.
- **The discovery zip** holds `bin/discovery` (and `discovery.bat`) and its jars.
- **Record the checksums** with the change. Section 4 compares the servers against them.
- **Build in CI rather than on a laptop,** so the commit in `VERSION` is one that passed every suite (go-live checklist, item 1).

## 4. Install the files on each IDM server

**Tested,** into a running IDM and into a stopped one.

1. **Unpack** the connector zip into a staging directory, not straight over `<idm>`: `samples/` and `VERSION` don't belong in the IDM installation.
2. **Copy** `connectors/graphentity/` and `script/lib/graphEntityPayload.js` into `<idm>`, keeping the directory structure. In sources mode the library must stay under `lib/au/com/azwork/idm/graphentity/…`; a flattened copy does not compile.
3. **Ownership and permissions.** IDM's process user must be able to read every file. In the ForgeRock image that user is uid 11111, group 0. Make the files writable only by your deployment process (security review R4).
4. **Keep `VERSION`** next to the files, for example as `<idm>/connectors/graphentity/VERSION`, so anyone can tell which release a server runs.
5. **Restart IDM?** Not for a first installation: IDM finds the scripts when the connector is first configured (§6). For an upgrade, see §12.

To check a server against the release:

```bash
cd <idm> && find connectors/graphentity script/lib/graphEntityPayload.js -type f | sort | xargs sha256sum > /tmp/installed.sha256
# compare with the same command run on the unpacked release
```

## 5. Network: TLS, proxies and timeouts

### 5.1 TLS

**Tested:** `integration/…/NetworkInIdmSpec`, with a private CA imported into IDM's trust store.

- **Which trust store.** The connector trusts what IDM's JVM trusts: `javax.net.ssl.trustStore`, which IDM sets to `<idm>/security/truststore` (JKS; password `changeit` unless your deployment changed it, `openidm.truststore.password`). It is not the operating system's store.
- **A certificate from a public CA** needs nothing: IDM's trust store carries the usual public roots.
- **A certificate from a private CA:** import the CA's certificate, then restart IDM. The JVM reads its trust store once, at start-up.

  ```bash
  keytool -importcert -noprompt -alias graphentity-service-ca -file service-ca.pem \
          -keystore <idm>/security/truststore -storepass changeit
  chown 11111:0 <idm>/security/truststore && chmod 600 <idm>/security/truststore   # as it was
  ```

  **Keep the trust store's owner.** If the file ends up owned by another user (root, say, after a copy), IDM cannot read it and **does not start**. Its log shows `Unable to load mainTrustStore keystore … (Permission denied)`. Seen in testing.
- **The host name must match.** The connector checks the service's host name against the certificate's subject alternative names. Use the name the certificate was issued for in `serviceAddress`, not an IP address unless the certificate lists it.
- **What failures look like.** The Test operation fails, and IDM's log shows the cause:
  - an untrusted CA: `unable to find valid certification path to requested target`;
  - a wrong host name: `Certificate for <localhost> doesn't match any of the subject alternative names`.

  In both cases nothing reaches the service, the key included. Both are tested.
- **Client certificates (mutual TLS)** are not supported: the service authenticates by API key alone (P13).
- **Plain http** is accepted with a WARN for hosts other than localhost (security review R6). Production must use https.

### 5.2 An outbound proxy

**Tested for http**, in IDM: every request goes through the proxy. Proxy authentication is tested in the connector's unit suite only. **Not tested:** https through the proxy, which uses `CONNECT`.

- **The settings,** all in the provisioner's `configurationProperties`:
  - `proxyAddress`: for example `"http://proxy.example.com:3128"`;
  - `proxyUsername` and `proxyPassword`, if the proxy needs authentication.

  These are the Scripted REST connector's own setting names, which IDM's admin UI shows. IDM encrypts `proxyPassword` like `password`.
- **Who applies them.** The Scripted REST connector does not apply them itself: it leaves that to the customizer script, and this connector's customizer does it (`ClientCustomizer.proxy`).
  - **Before this release, the proxy settings were ignored.** The connector went direct even with a proxy configured, which the integration suite found.
  - **The credentials go to the proxy alone.** They answer the proxy's `407` challenge, as `Proxy-Authorization`, and are never sent to the service.
  - **Refused:** a `proxyAddress` with credentials in it (`http://user:pass@…`), or one that isn't http or https. The address is not repeated in the error.
- **The JVM's `https.proxyHost` and friends are not used.** The connector builds its own HTTP client, so set the proxy in the provisioner.
- **To check:** the Test operation passes, and your proxy's log shows `POST <service>/admin/entities/search`.

### 5.3 Firewalls and timeouts

- **Firewalls:** every IDM server that runs reconciliation or implicit sync needs outbound access to the service's host and port. In a cluster, that is every node (§11.3).
- **Timeouts:** `connectTimeoutMs` (default 10,000) and `socketTimeoutMs` (default 60,000) bound every request, so a stalled service cannot hang IDM's threads. Raise `socketTimeoutMs` only if the service is known to be slow, and never to 0, which waits forever.

## 6. Configure the connector

### 6.1 Generate the configuration with the discovery tool

**Tested.** On the workstation:

```bash
unzip graphentity-discovery-<version>.zip
curl … /openidm/config/managed > managed.json        # or take it from your configuration repository
graphentity-discovery-<version>/bin/discovery --managed managed.json --types user,account \
    --answers answers.json --current graphentity-connector-<version>/samples/provisioner.openicf-graphentity.json \
    --out generated
```

- **`answers.json`** records your decisions for each synced type: its entity kind (subject or resource), its ID property, its archetypes, and any relationship overrides. The integration fixture `integration/src/test/resources/idm/answers.json` is a complete example. Without it, the tool proposes defaults and says which.
- **Reading straight from IDM.** `--idm-url https://idm.example.com --idm-user <account>` does that, with the password in `IDM_DISCOVERY_PASSWORD`. It makes one GET of `config/managed`, so the account needs read access to that alone.
- **Review what it prints:** warnings, errors, and the difference from the current provisioner. Nothing is written if there are errors.
- **It writes:**
  - `objectTypes.json`;
  - `customConfiguration.txt` and `.json`;
  - `provisioner.openicf-graphentity.json`, with `--current`;
  - one `sync-<type>.json` per type.

### 6.2 Set the service address and the key

Edit `generated/provisioner.openicf-graphentity.json`:
- **`serviceAddress`:** the service's https base URL, with no path and no credentials.
- **`password`:** the API key. IDM encrypts it when the configuration is saved. Put it in on the machine you load from, at the last moment, and delete the file afterwards; or type it into the admin UI instead.
- **Leave `username` empty and `defaultAuthMethod` as `NONE`,** so IDM adds no credentials of its own.
- **Remove the `_comment` entries.**
- **`proxyAddress`,** if there is a proxy (§5.2).

### 6.3 Generate the object types, then save once

**Tested.**

```bash
curl … -X POST '/openidm/system?_action=createFullConfig' --data @provisioner.json > full.json
curl … -X PUT  '/openidm/config/provisioner.openicf/graphentity' --data @full.json
```

- **`createFullConfig` comes first.** It runs the Schema script and returns the provisioner with its `objectTypes`; IDM does not fill them in by itself (H10). Saving first and then calling it initialises the connector twice at once. On a fresh IDM that fails, with a `LinkageError` or a Groovy `BUG! exception` (H11).
- **One provisioner change at a time (H21).** IDM silently discards a save that arrives while it is still applying the previous one. It answers 200, but keeps the earlier configuration. After each save:
  1. wait for `OpenICF Provisioner Service component graphentity is activated` in `<idm>/logs/openidm0.log.0`;
  2. check that `GET config/provisioner.openicf/graphentity` shows your change.

  In scripts mode, and on a small host, applying a save takes longer, so the window is wider.
- **`full.json` holds the key in clear.** Delete it once the save is confirmed.

### 6.4 Check the connector

**Tested.**
- `POST /openidm/system/graphentity?_action=test` answers `"ok": true`.
- Its `objectTypes` include every synced type.
- `GET /openidm/system/graphentity/user?_queryFilter=true&_pageSize=1` answers. Use each type.
- IDM's log has no `SEVERE` from `graphentity`. A `WARNING: The service has no manifests` means the service has no archetype manifests to check against (P22). It is harmless, but tell the service team.

## 7. Settings reference

The provisioner's `configurationProperties`. The connector-specific settings travel inside `customConfiguration`, a Groovy ConfigSlurper string that the discovery tool writes (`key=value; key='text'; …`).

| Setting | Where | Default | Meaning |
|---|---|---|---|
| `serviceAddress` | property | — (required) | The service's base URL. Must be http or https, with a host and no credentials |
| `password` | property | — (required) | The API key. Encrypted by IDM. Must have no control characters |
| `username` | property | empty | Leave empty |
| `defaultAuthMethod` | property | `NONE` | Leave `NONE`, or IDM adds a Basic header |
| `proxyAddress`, `proxyUsername`, `proxyPassword` | property | none | Outbound proxy (§5.2) |
| `scriptRoots`, `classpath` | property | `&{idm.instance.dir}/connectors/graphentity/scripts`, `…/lib` | Where the scripts and the library are. For the jar mode, `classpath` names the jar |
| `objectTypes` | `customConfiguration` | — (required) | The synced types: IDM resource, entity kind, ID property, attributes, archetypes and relationships. Generated (§6.1); don't hand-edit |
| `pageSizeDefault` | `customConfiguration` | 200 | Page size for searches, 1 to 1,000 |
| `byIdLookup` | `customConfiguration` | `get` | How a read by ID is made: `get` (`GET /admin/entities/{id}`), or `search` (a filtered search). Use `search` if the service's GET by ID fails (C1) |
| `deleteMissingTolerated` | `customConfiguration` | `true` | A delete of an entity the service doesn't have counts as done. `false` makes it an `UnknownUid` error |
| `rePutOnDroppedEdges` | `customConfiguration` | `false` | After a write whose relationships the service dropped, write once more (design §9.1). Off: the drop is logged at WARN and healed by the other entity's write |
| `apiKeyHeader` | `customConfiguration` | `X-API-KEY` | The header that carries the key |
| `connectTimeoutMs`, `socketTimeoutMs` | `customConfiguration` | 10,000, 60,000 | Timeouts for every request, in milliseconds |
| `readRateLimit`, `writeRateLimit` | property | none | The Scripted REST connector's own request rate limits. Not used or tested with this connector. The service answers 429 when it is overloaded, and IDM retries those (H19) |

Changing any setting is a provisioner save: one at a time, then verify (§6.3).

## 8. Managed objects

**Tested** (the integration fixture's `managed.json`).
- **Reverse properties.** Every relationship property you sync needs `reversePropertyName` on both sides. The discovery tool reports any that lack it.
- **The ID-change guard.** For each synced type, add the guard as its `onUpdate` script (runbook §6.4). It refuses a change to the type's ID property, which would otherwise create a second entity in the service:

  ```json
  "onUpdate": { "type": "text/javascript",
                "source": "require('lib/graphEntityPayload').onIdPropertyChange(newObject, oldObject, 'user');" }
  ```

  If the type already has an `onUpdate` script, call the guard from inside it.
- **`/` in IDs.** IDs must not contain `/`, which the service cannot address. IDM's default `userName` policy already forbids it. For other types, add the `cannot-contain-characters` policy, as the fixture's `account` does.

## 9. Mappings

**Tested.**
1. **Lint** each generated mapping:

   ```bash
   bin/discovery --lint generated/sync-user.json generated/sync-account.json
   ```

   It enforces the two rules on the `entityRelationships` and `directArchetypes` mappings: `"source": ""` (H12) and no `condition`.
2. **Merge** them into `config/sync` (or `conf/sync.json`), with **`"enableSync": false`** on these mappings for the initial load.
3. **Generated settings:**
   - **Situation policies:** a managed delete deletes the entity in the service (`SOURCE_MISSING: DELETE`, H13). Entities found only in the service are reported, never deleted (P16).
   - **`taskThreads: 4`:** shown to converge under concurrent implicit sync (WS8.10).
   - **The dry run:** for a non-production dry run, generate with `--report-only` instead (runbook §10).
4. **The initial load:** runbook §3. Accounts and other resources first, then users; implicit sync stays off until it is done.

## 10. Schedules, then go live

**Tested.**
1. **Load the schedules.** Take `samples/schedule-recon-graphentity-account.json` and `…-user.json` from the release, remove `_comment`, and load each with `PUT /openidm/config/schedule/recon-graphentity-<type>`. Resources reconcile at 01:15 and users at 02:15, server time; adjust the times to your window (runbook §4).
2. **Turn implicit sync on:** `"enableSync": true` on the mappings.
3. **Set up monitoring:** runbook §5.

## 11. Deployment patterns

### 11.1 One IDM server, files on disk

**Tested.** That is sections 3–10 as written, and appendix A.

### 11.2 IDM in a container image

**Partly tested:** the image's layout, ownership and trust store are the ones tested. Baking the configuration into the image, rather than loading it over REST, is not tested.

Build an image with the files in place:

```dockerfile
FROM gcr.io/forgerock-io/idm:7.5.0
COPY --chown=11111:0 release/connectors/graphentity /opt/openidm/connectors/graphentity
COPY --chown=11111:0 release/script/lib/graphEntityPayload.js /opt/openidm/script/lib/graphEntityPayload.js
# Only for a private CA (§5.1); run as root, then hand the trust store back to IDM's user.
USER root
COPY service-ca.pem /tmp/service-ca.pem
RUN /opt/jdk/bin/keytool -importcert -noprompt -alias graphentity-service-ca -file /tmp/service-ca.pem \
        -keystore /opt/openidm/security/truststore -storepass changeit \
    && chown 11111:0 /opt/openidm/security/truststore && chmod 600 /opt/openidm/security/truststore \
    && rm /tmp/service-ca.pem
USER 11111
```

Then load the configuration over REST as in §6–§10, once per environment.

To bake the configuration into the image as well, put the result of `createFullConfig` in `conf/provisioner.openicf-graphentity.json`, and the mappings in `conf/sync.json`. Two problems remain:
- **The key does not belong in an image.** Supply it at run time, through IDM's property substitution or your secrets mechanism, and check that IDM encrypts it. This is not tested.
- **`objectTypes`.** The file must already contain them, since IDM does not fill them in (H10). Generate them once against a running IDM, and keep the result with the image's source.

### 11.3 An IDM cluster

**Not tested.** What follows is from how IDM clusters work: nodes share configuration through the repository, but each node reads scripts and libraries from its own disk.
- **The files go on every node** (§4), at the same release. A node without them fails every operation it runs for this connector. Check the checksums on each node.
- **Configuration is shared.** Save the provisioner, mappings and schedules once, through any node. Each node then initialises its own connector.
- **The rule against simultaneous saves (H21) applies cluster-wide.** It is worth checking, during the dry run, that a save is applied on every node: run the Test operation through each node.
- **Schedules** run on one node at a time. `concurrentExecution: false` keeps a reconciliation from overlapping itself.
- **Implicit sync** runs on whichever node handles the change, so every node needs network access to the service (§5.3).
- **To settle with the IDM platform team before go-live:** how files reach every node (image, configuration management, shared disk), and in what order nodes are upgraded (§12).

### 11.4 Hosted IDM (PingOne Advanced Identity Cloud)

**Not supported as built, and not tested.**
- **Why:** a hosted tenant doesn't let you place connector scripts or libraries on its servers.
- **The likely route:** run the Scripted REST connector in a **Remote Connector Server (RCS)** that you operate. The scripts and the library would sit on the RCS's disk, and the tenant would reach the connector through the RCS. The mapping library (`graphEntityPayload.js`) would then have to be loaded into the tenant as a script.
- **Unknowns before relying on it:** whether the library compiles under the RCS's Groovy, and whether the mapping library can be loaded that way. Both are untested.
- **Treat this as a new piece of work,** with its own integration run.

## 12. Upgrading the connector

**Partly tested:** the restart is tested; replacing files under a running connector is not.

1. **Build and check** the new release (§3). Read its changes for configuration changes: new settings, or a regenerated `objectTypes`.
2. **Replace the files** on each server (§4). Remove the old `connectors/graphentity/lib/` first, so no stale class is left behind, especially when switching between sources and jar.
3. **Restart IDM,** one node at a time in a cluster. A restart makes IDM load the new scripts and library. Re-saving the provisioner reinitialises the connector too, but whether that picks up changed library files without a restart was not tested.
4. **Regenerate configuration** if the release changes it: §6.1 to §6.3, `createFullConfig` included.
5. **Check:** §6.4, then one reconciliation of each type, reviewed as in runbook §5.

A new IDM version is runbook §11.

## 13. Rollback and removal

### 13.1 Rollback to the previous release

**Not tested as a sequence.** It is §12 with the previous release:
1. **Before each upgrade, keep** the previous release zip and an export of the four configurations (`provisioner.openicf/graphentity`, `sync`, `managed`, and the two schedules).
2. **To roll back:** restore the files, restore the configurations one at a time (H21), restart IDM, and check (§6.4).
3. **Writes are not undone.** Anything the new release wrote to the service stays written. Reconciliation with the previous release restates every linked entity from IDM's state, which is how to repair the service.

### 13.2 Removing the connector

**Tested** (appendix A, step 12). In this order:
1. **Delete the schedules:** `DELETE /openidm/config/schedule/recon-graphentity-<type>`.
2. **Remove the mappings** from `config/sync`.
3. **Remove the ID-change guards** from `config/managed`: the `onUpdate` scripts, or the call inside them. The guard needs `script/lib/graphEntityPayload.js`, so it must go before the file does.
4. **Delete the provisioner:** `DELETE /openidm/config/provisioner.openicf/graphentity`. `system/graphentity` then answers 404.
5. **Delete the files** on every server: `connectors/graphentity/` and `script/lib/graphEntityPayload.js`. Remove the CA certificate from the trust store too, if nothing else uses it.
6. **Tell the service team.** Entities and relationships written to the service stay there, and the connector never deletes what it doesn't own (P16). Removing them is the service team's call.
